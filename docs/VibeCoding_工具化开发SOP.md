# VibeCoding 工具化开发 SOP

> 主题：从个人真实痛点出发，系统化判断是否值得开发工具，并把想法收敛成可落地、可验证、可产品化的工程方案。  
> 适用场景：AI 辅助开发、自用工具产品化、嵌入式工具链、调试自动化、脚本平台、数据分析工具、测试平台等。  
> 核心目标：避免一拍脑袋开发，减少伪需求、重复造轮子、需求跑偏和技术路线误判。

---

## 1. 为什么需要这套 SOP

在 VibeCoding 中，常见过程是：

```text
自己遇到一个真实问题
    ↓
催生一个工具想法
    ↓
让 AI 快速写代码
    ↓
功能越做越大
    ↓
发现需求边界不清楚
    ↓
发现已有工具已经解决一部分
    ↓
发现技术路线偏了
    ↓
工具做了一半，原始痛点却没解决好
```

典型问题包括：

```text
1. 需求不清晰
   做出来的东西偏离原始需求。

2. 伪需求
   一开始觉得很有价值，做着做着发现只是技术兴奋点。

3. 重复造轮子
   现有工具已经解决了 70%~90%，但前期没有调研。

4. 工具链不了解
   直到开发中后期才发现官方工具、开源工具或成熟方案。

5. MVP 失控
   本来只要解决一个痛点，最后变成想支持所有场景。

6. 技术路线先行
   先决定用某个技术，而不是先定义输入、输出和流程。

7. 没有停止条件
   遇到风险点后持续投入，无法判断是否应该暂停或换方向。
```

因此，工具开发必须从“写代码优先”转为：

```text
先验证问题，再验证方案，最后才写代码。
```

## 2. 总体流程

建议以后所有工具想法都按 9 个阶段推进：

```text
阶段 0：原始痛点记录
阶段 1：需求澄清
阶段 2：伪需求筛查
阶段 3：已有方案调研
阶段 4：Use / Wrap / Glue / Build 决策
阶段 5：MVP 定义
阶段 6：技术路线设计
阶段 7：Spike 技术验证
阶段 8：正式开发
阶段 9：复盘与产品化判断
```

核心原则：

```text
先痛点，后需求；
先调研，后自研；
先 MVP，后产品；
先诊断，后自动化；
先闭环，后泛化。
```

## 3. 阶段 0：原始痛点记录

### 3.1 目标

不要一开始就写：

```text
我要做一个工具。
```

而要先写清楚：

```text
我在什么场景下遇到了什么具体麻烦？
这个麻烦现在是怎么被解决的？
哪里慢？
哪里重复？
哪里容易出错？
```

工具想法往往会伪装成需求，但真正的需求通常隐藏在原始痛点里。

### 3.2 痛点卡模板

```markdown
# 痛点卡

## 场景
我在什么情况下遇到这个问题？

## 当前做法
现在我是怎么解决的？

## 痛苦点
哪里慢？哪里重复？哪里容易出错？

## 频率
这个问题多久发生一次？

## 成本
每次大概要浪费多少时间？

## 影响
影响调试效率、学习效率、交付效率，还是产品质量？

## 当前替代方案
现在有没有临时办法？

## 最原始需求
我真正想减少的动作是什么？
```

### 3.3 示例：KeilBridge

错误表述：

```text
我要做 Keil 转 CMake 工具。
```

更真实的痛点：

```text
公司工程基于 Keil。
Keil 调试信息 AI 看不到。
我需要人工截图、复制、转述变量、寄存器、调用栈、错误现象。
AI 无法主动打断点、读变量、分析故障。
我变成了 AI 和 Keil 之间的人工转接器。
这个流程效率低，而且信息损失严重。
```

真实需求：

```text
减少人工转述调试信息的成本，让 AI 能直接获得构建、下载、断点、变量、寄存器、调用栈、内存和故障现场等结构化信息。
```

## 4. 阶段 1：需求澄清

### 4.1 核心判断

每个工具想法都要先问：

```text
我到底要解决的是“结果问题”，还是“工具问题”？
```

错误方向：

```text
我要做 CMake 工具。
我要做 Keil 转 GCC 工具。
我要做一个万能转换器。
```

正确方向：

```text
我要减少人工转述调试信息的成本。
我要让 AI 能拿到结构化调试现场。
我要把嵌入式调试流程变成脚本可执行、结果可分析。
```

### 4.2 需求澄清五问

```text
1. 我现在最痛的动作是什么？
2. 这个动作是否重复发生？
3. 我想减少的是时间、错误率、认知负担，还是人工操作？
4. 这个问题不做工具能不能解决？
5. 最小可用方案是不是比我想象的简单？
```

### 4.3 输出：一句话真实需求

格式：

```text
我想把【当前重复/低效动作】变成【自动化/结构化/可复用流程】，从而减少【具体成本】。
```

示例：

```text
我想把 Keil 调试过程中的变量、寄存器、内存、调用栈和故障现场采集，变成可脚本化、可结构化输出的流程，从而减少我在 AI 和 Keil 之间人工转述调试信息的成本。
```

## 5. 阶段 2：伪需求筛查

### 5.1 什么是伪需求

伪需求不一定是假的，而是：

```text
1. 痛点不强
2. 频率不高
3. 已有工具已经解决
4. 只是技术好玩
5. 不是当前最该解决的问题
6. 工具复杂度远大于收益
7. 只对一个极小场景有用
```

### 5.2 伪需求筛查表

每个维度 1~5 分：

| 维度 | 问题 | 分数 |
|---|---|---|
| 高频性 | 这个问题是否经常发生？ | 1-5 |
| 痛苦程度 | 每次是否真的浪费很多时间？ | 1-5 |
| 可替代性 | 现有工具是否已经解决？反向打分 | 1-5 |
| 自动化收益 | 自动化后是否明显提效？ | 1-5 |
| 可落地性 | MVP 是否能短期做出来？ | 1-5 |
| 可复用性 | 是否能用于多个项目？ | 1-5 |

判断规则：

```text
总分 ≥ 24：
    值得做 MVP。

18 ~ 23：
    先做调研和 Spike 验证。

＜18：
    暂时不产品化，只记录想法。
```

### 5.3 KeilBridge 示例评分

```text
高频性：5
痛苦程度：5
可替代性：3
自动化收益：5
可落地性：3
可复用性：5
总分：26
```

结论：

```text
需求是真实的，但第一版范围必须严格控制。
```

## 6. 阶段 3：已有方案调研

### 6.1 为什么必须调研

很多工具失败，不是因为不会写代码，而是：

```text
1. 没有调研官方工具
2. 没有调研开源工具
3. 不知道已有生态已经解决了大部分问题
4. 直接进入自研，导致重复造轮子
5. 做到一半才发现更好的路线
```

硬规则：

```text
任何工具想法，写代码前必须做一轮已有方案调研。
```

### 6.2 调研目标

调研不是为了证明“不用做”，而是为了搞清楚：

```text
1. 哪些轮子已经存在？
2. 哪些轮子可以复用？
3. 哪些地方没有现成方案？
4. 我的工具到底是替代、组合、二开，还是胶水层？
```

### 6.3 调研范围

至少查：

```text
1. 官方工具
2. 开源工具
3. 商业工具
4. IDE 插件
5. 命令行工具
6. 协议/API
7. 社区成熟方案
8. 相邻领域方案
```

### 6.4 工具调研矩阵模板

```markdown
# 现有工具调研矩阵

| 工具 | 解决什么 | 不解决什么 | 是否复用 | 结论 |
|---|---|---|---|---|
| 工具 A | | | | |
| 工具 B | | | | |
```

### 6.5 调研后的关键判断

调研后必须能回答：

```text
我是不是在重复造轮子？
我应该复用什么？
我应该自研什么？
我的差异化价值到底在哪里？
```

## 7. 阶段 4：Use / Wrap / Glue / Build 决策

### 7.1 四种路线

| 路线 | 说明 | 适用场景 |
|---|---|---|
| Use | 直接使用现有工具 | 已有工具解决 80% 以上 |
| Wrap | 封装现有工具 | 工具可用但接口不顺手 |
| Glue | 多工具组合 | 单个工具不够，组合后能解决 |
| Build | 自研 | 现有工具没有覆盖核心需求 |

### 7.2 决策原则

```text
能 Use 就不要 Wrap；
能 Wrap 就不要 Glue；
能 Glue 就不要 Build；
必须 Build 的，只做差异化部分。
```

### 7.3 示例：KeilBridge

```text
CMake：
    Use，不自研构建系统。

GDB：
    Use，不自研调试协议。

OpenOCD / J-Link：
    Use，不自研烧录调试器。

Cortex-Debug：
    Learn，借鉴其 GDB/MI 调试流程，不重写 VS Code 插件。

Keil 工程解析：
    Build，这是差异化。

Doctor 诊断系统：
    Build，这是差异化。

AI JSON 接口：
    Build，这是差异化。

Debug Collector：
    Build，但底层调用 GDB/J-Link/OpenOCD。
```

## 8. 阶段 5：MVP 定义

### 8.1 MVP 原则

MVP 必须满足：

```text
1. 解决最核心痛点
2. 范围足够小
3. 能快速验证价值
4. 不追求架构完美
5. 不追求支持所有情况
```

公式：

```text
MVP = 最痛场景 + 最小自动化闭环 + 可观察结果
```

### 8.2 MVP 模板

```markdown
# MVP 定义

## 最核心痛点
一句话描述。

## 不做什么
明确排除范围。

## 输入
工具需要什么输入？

## 输出
工具产生什么结果？

## 成功标准
做到什么算成功？

## 失败标准
什么情况说明路线不对？

## 验证周期
几天内必须看到结果？
```

### 8.3 KeilBridge 正确 MVP

错误 MVP：

```text
支持 STM/GD 所有芯片。
支持标准库/CubeMX/RTOS。
支持 GCC/ArmClang。
支持所有 .lib。
支持所有调试器。
```

正确 MVP：

```text
输入一个已有 ELF/AXF。
连接 J-Link/OpenOCD。
reset halt。
检查向量表。
break main。
break HardFault。
continue。
读取寄存器、栈、变量、调用栈。
输出 debug_result.json。
```

## 9. 阶段 6：技术路线设计

### 9.1 技术路线不能从工具出发

错误方式：

```text
我要用 Python/Rust/CMake/Clang/React 做一个东西。
```

正确方式：

```text
输入是什么？
输出是什么？
中间需要哪些能力？
哪些能力已有工具提供？
哪些能力需要我写？
```

### 9.2 技术路线模板

```markdown
# 技术路线

## 输入
用户提供什么？

## 输出
工具生成什么？

## 核心流程
步骤 1：
步骤 2：
步骤 3：

## 复用工具
CMake：
GDB：
OpenOCD：
J-Link：

## 自研模块
模块 1：
模块 2：

## 高风险点
风险 1：
风险 2：

## 降级方案
方案 A：
方案 B：
```

### 9.3 技术路线设计原则

```text
1. 先定义输入输出
2. 再定义流程
3. 再选择工具
4. 最后决定自研模块
```

## 10. 阶段 7：Spike 技术验证

### 10.1 Spike 是什么

Spike 是：

```text
只验证最高风险技术点，不做完整产品。
```

### 10.2 为什么需要 Spike

很多项目失败不是需求错，而是最高风险点没有提前验证。

例如：

```text
1. GDB 能不能读取 ArmClang 生成的 ELF？
2. J-Link GDB Server 能不能稳定 reset/halt/read variable？
3. OpenOCD 对某个 GD32 型号支持是否稳定？
4. Keil .lib 是否能通过 ArmClang 后端兼容？
5. .uvprojx 是否能稳定解析出 source/include/define？
```

### 10.3 Spike 模板

```markdown
# Spike 验证

## 要验证的问题
一句话。

## 最小实验
用什么最小代码验证？

## 成功标准
什么现象说明可行？

## 失败标准
什么现象说明风险很大？

## 结论
继续 / 调整 / 放弃。
```

### 10.4 KeilBridge Spike 示例

```text
验证问题：
    不转 CMake，仅使用已有 AXF/ELF，能否用 GDB 自动断点并读取变量？

最小实验：
    用一个现有 Keil 工程生成 AXF。
    启动 J-Link GDB Server。
    用 GDB 脚本 break main、print 变量、dump 寄存器。

成功标准：
    能输出 JSON 形式的变量、寄存器、PC/MSP、断点命中信息。

失败标准：
    GDB 无法读取符号或连接不稳定。
```

## 11. 阶段 8：正式开发

### 11.1 开发原则

```text
1. 先做垂直闭环，再做横向适配。
2. 先支持一个芯片，再支持一个系列。
3. 先支持一个工程类型，再扩展多个类型。
4. 先输出报告，再自动修复。
5. 先人工确认，再自动执行危险动作。
```

### 11.2 垂直闭环优先

错误路线：

```text
先适配 20 种芯片。
```

正确路线：

```text
先把一个工程完整跑通：
    scan
    build
    flash
    debug
    dump
    report
```

然后再扩展：

```text
GD32 裸机
GD32 RTOS
STM32 标准库
STM32 CubeMX
STM32 RTOS
```

### 11.3 每个功能必须有退出条件

例如：

```text
功能：自动修复 ARMCC 语法

退出条件：
    第一版只生成 compat header 和 report，不直接改源码。
```

## 12. 阶段 9：复盘与产品化判断

### 12.1 复盘问题

```text
1. 原始痛点是否被解决？
2. 是否偏离了最初需求？
3. 哪些功能其实没用？
4. 哪些功能最有价值？
5. 用户是否愿意持续使用？
6. 是否值得产品化？
7. 下一步是扩展适配，还是重构架构？
```

### 12.2 产品化判断

只有满足这些条件，才值得产品化：

```text
1. 自己至少重复使用 3 次
2. 每次都明显节省时间
3. 换一个相似工程仍然有价值
4. 有清晰输入输出
5. 能生成稳定报告
6. 错误可诊断
7. 不依赖大量手工解释
```

不满足时，先当个人脚本，不急着产品化。

## 14. 避免跑偏的 6 条原则

### 14.1 永远从痛点出发，不从工具出发

不要说：

```text
我要做 CMake 工具。
```

要说：

```text
我要减少人工转述调试信息的成本。
```

### 14.2 先解决最痛的一刀

问自己：

```text
哪个功能能最快减少我的痛苦？
```

### 14.3 先 Glue，后 Build

优先组合已有工具：

```text
CMake 用现成的
GDB 用现成的
OpenOCD/J-Link 用现成的
CubeMX 用现成的
Keil CLI 用现成的
```

自己只做：

```text
桥接层
诊断层
结构化输出
AI 接口
```

### 14.4 先诊断，后自动修复

第一版：

```text
检测问题
解释问题
生成报告
给出建议
```

第二版再考虑：

```text
生成 compat header
生成 patch
自动替换 port.c
```

### 14.5 先单点闭环，再泛化

先跑通：

```text
一个工程
一个芯片
一个调试器
一个 debug 流程
```

再扩展到：

```text
多芯片
多厂商
多 RTOS
多后端
```

### 14.6 每次都要有停止线

例如：

```text
如果三天内无法证明 GDB 能稳定读取变量，
就暂停 CMake 转换，先回退到 Keil CLI + 手动导出。
```

## 15. 判断是否重复造轮子的方法

每次问：

```text
1. 有没有官方工具已经解决？
2. 有没有开源工具已经解决？
3. 我是不是只是嫌现有工具不好看？
4. 现有工具能不能通过脚本封装解决？
5. 我的工具是否只是已有工具的薄封装？
6. 我的差异化是不是足够明确？
```

如果答案是：

```text
现有工具能解决 80%，我只是重新写一遍。
```

那就是重复造轮子。

如果答案是：

```text
现有工具各自解决一段，但没有把它们连接成我的工作流。
```

那就不是重复造轮子，而是做胶水层。

```text
Step 4：做工具调研矩阵
Step 5：判断 Use / Wrap / Glue / Build
Step 6：定义 MVP，不超过 3 个核心功能
Step 7：列出不做什么
Step 8：做 Spike 验证最高风险点
Step 9：做垂直闭环
Step 10：生成报告和复盘
Step 11：决定是否产品化
```

硬规则：

```text
没有完成以下三个文档，不进入正式写代码：

1. 痛点卡
2. 工具调研矩阵
3. MVP 定义
```

---

## 17. 最终总结

VibeCoding 的强项是：

```text
快速把想法变成代码。
```

但它的风险是：

```text
太快进入实现，太晚发现需求和路线问题。
```

因此，成熟的工具开发方式应该是：

```text
先把真实痛点、已有工具、MVP、技术风险想清楚，
再让 AI 帮你实现最小闭环。
```

最终一句话：

```text
先痛点，后需求；
先调研，后自研；
先 MVP，后产品；
先诊断，后自动化；
先闭环，后泛化。
```
